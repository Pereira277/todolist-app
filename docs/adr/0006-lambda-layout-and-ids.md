# ADR-0006: One Lambda function per resource, UUID v4 identifiers

- **Status:** Accepted
- **Date:** 2026-10-21

## Context
v0.2 adds eight routes on top of `GET /me` (see the endpoint table in
`docs/architecture.md`): list CRUD under `/lists` and task CRUD under `/lists/{id}/tasks`.
Each Lambda function is a clickops resource (function, execution role, log group,
integration) until the Terraform migration, and the deploy pipeline updates every function's
code. List and task IDs are generated by the API and become part of the DynamoDB keys
(ADR-0002) and of the list URL (`/app/list/?id=<id>`).

## Options considered
Function layout:
1. **One function per route:** smallest blast radius and the tightest IAM per route, but
   eight functions, roles and log groups to create by hand and deploy, for handlers that
   share almost all their code.
2. **One function per resource (`todolist-lists`, `todolist-tasks`):** each function routes
   on `event.routeKey`. Two functions to manage, each one cohesive, and a bug or bad deploy
   in one resource does not take down the other.
3. **One function for the whole API:** a single deploy target, but every route shares one
   blast radius, one set of permissions and one log stream, and the router grows with every
   version.

Identifiers:
1. **UUID v4 from `crypto.randomUUID()`:** built into Node.js, no dependency, 122 random
   bits, unguessable. No time ordering.
2. **ULID or KSUID:** lexicographically sortable by creation time, so tasks would come back
   in order from the `Query`. Needs a dependency, and the timestamp prefix leaks when each
   item was created.
3. **Sequential counters:** short IDs, but they need an extra conditional write per create
   and make IDs guessable.

## Decision
**One function per resource** and **UUID v4 from `crypto.randomUUID()`**.

- `todolist-lists` handles `GET/POST /lists` and `PATCH/DELETE /lists/{id}`.
- `todolist-tasks` handles `GET/POST /lists/{id}/tasks` and
  `PATCH/DELETE /lists/{id}/tasks/{taskId}`; `GET /lists/{id}/tasks` returns the list's
  `META` with the tasks, since both come from the same `Query`.
- Each function has its own `src/handlers/<resource>.ts` entry point, bundled by esbuild into
  its own zip. Shared code (DynamoDB client, access check, validation, responses) lives in
  `src/lib/` and is bundled into both.
- `todolist-me` stays as it is.

Two functions balance isolation against clickops effort. UUID v4 needs no dependency, and
the only ordering we need (tasks by creation) is a sort in the handler over a partition we
already read in full.

## Consequences
- Positive: two more functions instead of eight; each resource deploys and fails on its own;
  IDs reveal nothing and need no coordination.
- Negative / trade-offs:
  - Each function routes internally, so a routing bug is ours, not API Gateway's.
  - Both functions need read and write on the same table, so splitting them does not narrow
    IAM much in v0.2.
  - Tasks are sorted in memory; fine while a list fits in one `Query` page (1 MB).
  - The deploy workflow must build and update three functions instead of one.
- What needs revisiting, and when: if a list could exceed one `Query` page, switch task IDs to
  a sortable format or add pagination; sharing (v0.3) may add a `todolist-shares` function
  under the same rule.

## SAA-C03 relevance
Lambda design for API Gateway integrations, blast radius and least privilege per function,
operational overhead versus isolation, choosing partition and sort key values.
